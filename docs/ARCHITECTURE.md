# OmniLive architecture

## Live path

```text
Android Camera2
  -> WebRTC Android SDK + hardware codec
  -> direct ICE path when possible, TURN relay when required
  -> Modal L4 ASGI container
  -> persistent /v1/live WebSocket pins the session container
  -> aiortc remote video track
  -> LatestFrameSource (one fresh decoded frame, no queue growth)
  -> periodic detector + sparse landmark/feature tracker
  -> localized crop processor
  -> temporal transform reuse within confidence/TTL limits
  -> feather/color-matched composite
  -> aiortc return track
  -> WebRTC downlink
  -> Android hardware decoder
  -> ReturnedVideoBus / local renderer
```

The Android offer is now exchanged over the same long-lived WebSocket that keeps the live GPU input active. Session creation for the live path happens inside that pinned worker, so the in-memory session state and aiortc peer cannot accidentally be split across unrelated Modal containers.

The older HTTP session and offer endpoints remain for compatibility and diagnostics.

## ICE and TURN

Both Android and the backend aiortc PeerConnection consume the same dynamic ICE configuration.

OmniLive supports:
- static ICE username/password configuration
- coturn-compatible TURN REST shared-secret credentials generated by the backend
- credential TTL capped to the bootstrap session TTL
- arbitrary STUN/TURN URLs via environment configuration

Permanent TURN shared secrets never need to be sent to Android.

## Latency strategy

- one live WebSocket input per L4 container during MVP benchmarking
- latest-frame overwrite instead of processor backlog
- process a localized region rather than the whole frame for custom models
- detector cadence lower than camera/tracker cadence
- independent neural inference FPS budget
- fast overload degradation and slower recovery
- short transform-cache TTL with tracker-confidence invalidation
- hardware encode/decode on Android where available
- adaptive capture resolution/FPS from RTT, loss, and backend p95
- worker-local telemetry returned over the pinned WebSocket

Target added round-trip latency remains below 250 ms, with a stretch target around 150-180 ms on a good network.

## Session model

A live session has a random ID, short-lived bootstrap bearer token, quality profile, effect profile, expiry metadata, and monotonic frame sequencing support.

The bootstrap token can expire after the live WebSocket has been established without terminating an already-authenticated active call. The WebSocket itself owns the lifetime of the live worker peer.

No video frames are persisted by default.

## Modal MVP topology

The current L4 ASGI deployment is intentionally a single live-media service. `@modal.concurrent(max_inputs=1)` makes the one-session-per-container benchmarking assumption explicit, and the live WebSocket keeps that input active.

This is appropriate for latency validation. It is not the intended cost-optimized multi-user topology.

The later scale topology is:

```text
cheap CPU signalling/control
        -> session allocation
        -> session-affine GPU media worker
        -> TURN/direct WebRTC media
```

Do not split this until real L4 measurements establish the worker lifecycle, model cost, and target concurrency.
